# Azure 订阅到手后的安全基线：MFA、角色分配、活动日志与网络入口

Azure 的权限模型比很多人想象的多一层：登录身份由 Microsoft Entra ID（原 Azure AD）管理，资源权限由订阅上的 RBAC 角色分配决定，两边都要检查。不少团队只改了登录密码就开始建虚拟机，结果几个月后才发现订阅上还挂着不认识的 Owner，或者某台 VM 的 3389 端口对全网开放。

这篇把安全基线拆成五步，适合刚完成 [Azure 开户](https://www.clouddalao.com/cloud/azure) 或刚接手一个已有订阅的团队。建议在部署正式业务之前一次性做完，并把每一步的结果记进团队的运维文档。控制台菜单名称以微软官方最新界面为准。

## 第一步：确认你到底拿到了什么

动手之前先把"账号""租户""订阅"三件事分清楚，后面所有检查都依赖它：

| 要确认的项 | 在哪里看 | 记录什么 |
| :--- | :--- | :--- |
| 登录账号 | 门户右上角头像 | 登录邮箱 / UPN，是否为租户内成员用户 |
| 租户（Tenant） | Microsoft Entra ID → 概述 | 租户 ID、主域名 |
| 订阅 | 订阅（Subscriptions）列表 | 订阅 ID、订阅类型、状态 |
| 你的角色 | 订阅 → 访问控制 (IAM) → 我的访问权限 | 是否为 Owner |

订阅类型会影响配额和可用服务，如果还不确定手里是哪种订阅，可以先看 [Azure 订阅类型与配额说明](https://www.clouddalao.com/guides/azure-subscription-types-and-quota)。

检查点：订阅状态为"已启用"，你本人在订阅上是 Owner，并且租户 ID、订阅 ID 已写进台账。

## 第二步：身份加固，先把 MFA 落实

Entra ID 是所有入口的总闸，这一步做好，后面的风险会小很多。

1. **修改初始密码**：换成只有负责人知道的强密码，保存在团队的密码管理工具里，不要发在聊天群。
2. **启用 MFA**：小团队最省事的方式是在 Entra ID → 属性 → 管理安全默认值，确认"安全默认值"处于开启状态，它会要求所有用户注册 MFA，并阻止旧式身份验证协议。如果租户有条件访问（Conditional Access）许可，也可以改用条件访问策略做更细的控制，但两者不要同时混用。
3. **核对全局管理员**：Entra ID → 角色和管理员 → 全局管理员，列表里只应该有团队明确授权的人。全局管理员可以提升自己对所有订阅的访问权，是比订阅 Owner 更高的一层。
4. **准备应急账号**：建一个不日常使用的"破窗"管理员账号，设置独立的强密码和 MFA，凭据离线保管，防止唯一管理员丢失手机后整个租户无法登录。
5. **更新联系方式**：把账号的备用邮箱、手机换成团队长期使用、人员离职也不会失效的地址。

检查点：所有管理员都已注册 MFA；全局管理员不超过两到三人；应急账号存在且有登录记录可查。

## 第三步：清理订阅上的角色分配

Azure 的资源权限通过"安全主体 + 角色 + 作用域"三要素定义。接手一个订阅时，最常见的隐患就是遗留的角色分配。

打开 订阅 → 访问控制 (IAM) → 角色分配，逐条检查：

- **Owner**：能管理资源，也能给别人分配权限。只保留负责人和应急账号。
- **Contributor（参与者）**：能管理资源但不能分配权限，适合日常运维的工程师。
- **Reader（读者）**：只读，适合财务、审计或外部顾问。
- **服务主体 / 托管标识**：给 CI/CD、脚本用的应用身份。逐个确认用途，不认识的先记录再删除。

几条实用原则：

1. 权限尽量分配在资源组上，而不是整个订阅上。生产、测试分开资源组，工程师只拿自己负责的那一组。
2. 来宾用户（外部邮箱邀请的账号）在角色分配里会单独标出，接手后要重点核对。
3. 程序调用不要复用个人账号，改用服务主体或托管标识，并给它最小的角色。
4. 服务主体的客户端密码有过期时间，到期前要轮换，轮换记录写进台账。

检查点：角色分配表里每一行都能说出"这是谁、为什么需要这个权限"；订阅级 Owner 不超过两个。

## 第四步：让操作可追溯——活动日志与诊断设置

Azure 活动日志（Activity Log）记录订阅上的管理操作，例如谁创建了虚拟机、谁修改了网络安全组、谁新增了角色分配。它默认在门户里保留 90 天，超过时间就查不到了。

建议这样配置：

1. 订阅 → 活动日志 → 导出活动日志（诊断设置），把日志发送到一个 Log Analytics 工作区或存储账户，用于长期留存。
2. 存放日志的存储账户或工作区放在单独的资源组里，只给少数人写权限，避免日志被随手删除。
3. 针对高风险操作建告警规则，例如"创建或更新角色分配""删除网络安全组规则"，通知发到团队公共邮箱。
4. Entra ID 的登录日志和审核日志也值得保留，用来排查异常登录。

注意，日志工作区和存储账户本身会产生费用，建好之后顺手在成本管理里看一眼。

检查点：随便改一条测试资源的标签，几分钟后能在活动日志里查到这条记录和操作人。

## 第五步：收紧网络入口

被扫描、被爆破的大多是公网直接暴露的管理端口。上线前把入口按下面的清单过一遍：

| 场景 | 不推荐 | 推荐 |
| :--- | :--- | :--- |
| Linux 远程登录 | NSG 对 0.0.0.0/0 放行 22 | 只放行办公出口 IP，或通过 Azure Bastion 登录 |
| Windows 远程桌面 | NSG 对全网放行 3389 | Azure Bastion，或按需开放的 JIT 访问 |
| 数据库 | 绑定公网 IP 直接访问 | 放在虚拟网络内，用私有终结点访问 |
| 管理后台 | 直接暴露公网 | 加 IP 白名单或放在 VPN 之后 |

操作建议：

1. 网络安全组（NSG）规则优先绑定在子网上，统一管理，再按需给个别网卡加规则。
2. 每条入站规则写清楚描述，说明用途和申请人，方便日后清理。
3. Linux 虚拟机使用 SSH 公钥登录，关闭密码登录。
4. 不再使用的公网 IP 及时释放，它既是暴露面也会持续计费。

检查点：用外部网络扫描自己的公网 IP，除业务端口（如 80/443）外没有开放的管理端口。

## 补充：打开 Defender for Cloud 看一眼

Microsoft Defender for Cloud 的基础安全态势管理功能可以直接在订阅上查看安全建议，例如"应为订阅指定多个所有者""虚拟机的管理端口应关闭"。建议在完成上面五步后打开它，把"建议"页里的高风险项逐条处理或标注豁免原因。更深入的工作负载保护计划是收费的，是否开启按业务需要决定，开启前先确认计费方式。

## 别忘了费用这一侧

安全问题和费用问题常常是同一件事：被盗用的账号往往表现为突然暴涨的账单，而余额耗尽又可能导致订阅被禁用、业务中断。所以在做安全基线的同时，建议在 成本管理 → 预算 里给订阅设一个月度预算和多档提醒，具体做法可以参考 [云预算告警：避免余额不足导致停机](https://www.clouddalao.com/guides/cloud-budget-alerts-avoid-suspension)。需要给账号补充余额时，走 [充值](https://www.clouddalao.com/recharge) 流程，并把每笔记录对应到订阅 ID。

## 一页检查清单

- [ ] 租户 ID、订阅 ID、订阅类型已记入台账
- [ ] 安全默认值或条件访问已启用，所有管理员完成 MFA 注册
- [ ] 全局管理员和订阅 Owner 名单已核对，只保留必要人员
- [ ] 应急管理员账号已创建，凭据离线保管
- [ ] 遗留的角色分配、来宾用户、服务主体已逐条确认
- [ ] 活动日志已导出到长期存储，高风险操作已配置告警
- [ ] NSG 中没有对全网开放的 22 / 3389 端口
- [ ] Defender for Cloud 的高风险建议已处理或标注原因
- [ ] 月度预算和费用提醒已配置

这份清单建议每季度复查一次，人员变动、项目交接时也要重新过一遍。如果你在 Azure 开户、订阅选择或后续充值上有疑问，可以回到 [云大佬首页](https://www.clouddalao.com/) 联系客服。
