# 云账号 AccessKey 泄露后的一小时：阿里云国际、腾讯云国际与 AWS 通用应急清单

密钥泄露最常见的路径并不复杂：把配置文件连同密钥一起提交到公开仓库，在工作群里贴了一段带密钥的脚本，或者离职同事的电脑里还留着旧凭证。一旦发生，最怕的不是"不知道怎么办"，而是顺序做错，比如先删资源、后停密钥，结果攻击者继续创建新的。这篇把应急过程拆成六步，按顺序做，每一步都有明确的完成标准。

> 控制台菜单名称以各平台官方最新界面为准。本文只讲通用顺序，不替代平台官方的安全公告和工单流程。

## 先判断：泄露的是哪一种凭证

| 凭证类型 | 典型形态 | 影响范围 | 处理优先级 |
| :--- | :--- | :--- | :--- |
| 主账号 AccessKey | 阿里云国际主账号 AccessKey、AWS 根用户访问密钥 | 整个账号 | 最高，立刻停用 |
| 子用户 / IAM 用户密钥 | RAM、CAM、IAM 用户创建的密钥 | 取决于授予的权限 | 高，权限越大越急 |
| 临时凭证 | STS 或临时安全令牌 | 到期前有效 | 中，吊销会话并缩短有效期 |
| 控制台登录密码 | 子账号登录口令 | 取决于权限 | 高，重置并开启 MFA |

如果不确定泄露的是哪一类，一律按范围最大的情况处理，等排查清楚再放宽。

## 第一步：停用密钥，而不是先删除

前十分钟只做一件事，把泄露的密钥置为停用状态。

1. 登录对应平台控制台，进入访问控制页面（阿里云国际是 RAM，腾讯云国际是 CAM，AWS 是 IAM）。
2. 找到泄露的那一组密钥，把状态改为"禁用 / 停用 / Inactive"。
3. 先不要删除。停用立即生效，同时保留密钥 ID，后面查操作记录要用它来过滤。
4. 如果泄露的是主账号级别的密钥，直接停用，之后再用子用户替代，不要继续使用主账号密钥。

完成标准：用泄露的密钥再调用一次接口，返回的是"密钥被禁用"一类的错误。

## 第二步：用操作审计记录还原攻击者做了什么

三家平台都有记录 API 调用的审计服务，阿里云国际有操作审计，腾讯云国际有操作审计，AWS 有 CloudTrail。查询时按下面三个条件过滤：

- 访问密钥 ID 等于泄露的那一组。
- 时间范围从密钥可能开始暴露的时间算起，不要只看今天。
- 重点关注创建类操作：创建实例、创建子用户、创建新密钥、修改安全组、修改存储桶权限、开通新服务。

把查到的操作按时间记成清单，每一条标注"确认是自己人做的 / 确认是攻击者做的 / 无法判断"。无法判断的先按攻击者处理。

## 第三步：清理攻击者留下的东西

只处理第二步清单里确认或疑似由泄露密钥产生的内容：

| 类别 | 检查点 |
| :--- | :--- |
| 计算资源 | 陌生实例、陌生地域里的实例，尤其是自己从没用过的地域 |
| 访问权限 | 新增的子用户、新增的密钥、新增的登录配置或信任关系 |
| 网络入口 | 被放开的安全组端口、被修改的防火墙规则 |
| 存储与数据 | 存储桶是否被改成公开、是否有陌生文件或被下载的痕迹 |
| 其他服务 | 陌生的函数、容器集群、消息队列、域名解析记录 |

清理前先截图或导出配置，方便之后向平台说明情况。需要保留的业务资源不要误删，拿不准的先停止而不是删除。

## 第四步：轮换凭证并改成更安全的用法

1. 给业务创建新的子用户或角色，只授予它实际需要的权限，权限设计思路可参考 [阿里云国际 RAM 访问控制入门](https://www.clouddalao.com/guides/alibaba-cloud-ram-users-permissions)。
2. 新密钥不要写进代码仓库，改放环境变量、云平台的密钥管理服务或部署平台的保密配置里。
3. 在代码仓库里启用密钥扫描和提交前检查，避免同样的错误再发生一次。
4. 把仓库历史里已经提交过的密钥视为永久泄露，只改文件内容并不能消除历史记录，旧密钥必须保持停用。
5. 所有人重新核对主账号的 MFA 是否开启，账号刚交付时的安全设置清单可对照 [AWS 账号交付后的安全设置清单](https://www.clouddalao.com/guides/aws-account-security-after-handover)。

## 第五步：补上费用侧的保护

密钥泄露最直接的后果往往是账单。处理完安全问题后，检查余额变化和账单明细，确认有没有不属于自己业务的扣费。

- 打开费用中心，按服务和地域查看最近的消费，找出突然出现的陌生项目。
- 设置余额不足或消费超限的提醒，具体做法见 [国际云余额告警与预算设置](https://www.clouddalao.com/guides/cloud-budget-alerts-avoid-suspension)。
- 如果发现异常扣费，保留审计记录、资源清单和账单截图，通过平台工单说明情况。是否能够减免由平台根据自己的政策决定，不要对结果提前做任何假设。

## 第六步：复盘并写进团队规范

应急结束后，用十分钟写一页复盘，至少包含这几项：

- 泄露的时间、发现的时间、停用的时间，三者之间的间隔。
- 泄露的渠道：公开仓库、聊天群、离职交接、还是本地文件。
- 实际造成的影响：创建了哪些资源、产生了多少费用、是否涉及数据。
- 之后的改动：谁来保管密钥、多久轮换一次、权限怎么划分、告警发给谁。

## 一页速查表

| 顺序 | 动作 | 完成标准 |
| :--- | :--- | :--- |
| 1 | 停用泄露的密钥 | 用旧密钥调用接口被拒绝 |
| 2 | 按密钥 ID 查审计记录 | 得到按时间排列的操作清单 |
| 3 | 清理异常资源与权限 | 清单中每一条都有处理结论 |
| 4 | 轮换并改用更安全的存放方式 | 代码仓库中没有明文密钥 |
| 5 | 检查账单并设置提醒 | 提醒已开启，异常扣费已留证据 |
| 6 | 写复盘并更新团队规范 | 保管人和轮换周期已确定 |

## 常见问题

**密钥只在私有仓库里出现过，也要停用吗？**
建议要。私有仓库的访问范围会变化，协作者也可能把代码拷到别处，轮换一次的成本远低于排查一次风险。

**不知道是哪个密钥泄露了怎么办？**
先在访问控制页面看每个密钥的最近使用时间，把长期不用的直接停用，再逐个核对正在使用的，必要时一次性全部轮换。

**账号是新拿到的，也需要做这些吗？**
需要。新账号交付后第一件事就是核对安全设置，建议先按各平台的开户后检查清单走一遍。还没有账号的团队，可以先看 [阿里云国际开户](https://www.clouddalao.com/cloud/aliyun-intl) 和 [AWS 开户](https://www.clouddalao.com/cloud/aws) 的介绍，再决定适合自己的平台。

把"停用、查记录、清理、轮换、查账单、复盘"这六个动作固定成团队的应急流程，下次遇到问题，就能直接照着做，而不用临场想顺序。
