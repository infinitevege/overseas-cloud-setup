# 腾讯云国际新账号安全基线：MFA、CAM、操作审计与安全组

腾讯云国际（tencentcloud.com）账号到手后，最常见的误区是：先开 CVM 部署业务，几周后才发现主账号没开 MFA、日常还在用根账号登录、安全组对全网放行了 22 端口、被异常操作也没人能追溯。安全基线不是“上线后再补”，而是正式业务前必须一次性做完的门槛。

这篇按六步拆解，适合刚完成 [腾讯云国际开户](https://www.clouddalao.com/cloud/tencent-intl) 或刚接手一个已有主账号的团队。控制台菜单名称以官方最新界面为准，界面改版时以控制台实际路径为准。

## 第一步：登录与身份核对

动手之前先确认你拿到的到底是什么账号，后面所有检查都依赖它：

| 要确认的项 | 在哪里看 | 记录什么 |
| :--- | :--- | :--- |
| 账号 UID / Account ID | 控制台右上角头像 → 账号信息 | 与交付信息一致，记入团队台账 |
| 登录身份 | 账号信息页 / 登录提示 | 是主账号（根账号），还是 CAM 用户 |
| 站点 | 浏览器地址栏 | `tencentcloud.com` 国际站，不是国内站 `cloud.tencent.com` |
| 初始余额 | 费用中心 → 账户概览 | 与订单到账金额一致 |

UID 是后续 [充值](https://www.clouddalao.com/recharge) 时唯一要填的账号标识，建议当天就写进密码管理工具的备注。如果还没开户，先走 [开户](https://www.clouddalao.com/open-account) 流程拿到正式账号再继续下面的步骤。

检查点：UID、站点、登录身份三项已记入台账，且确认是国际站主账号。

## 第二步：登录保护——密码、MFA、联系方式

主账号是整个云资源的总闸，这一步做好，后面的风险会小很多。

1. **修改初始密码**：换成只有负责人知道的强密码，保存在团队的密码管理工具里，不要发在聊天群或邮件明文。
2. **启用 MFA**：在账号安全相关页面绑定虚拟 MFA（任意 TOTP 身份验证器 App 均可）。把恢复码 / 备用方式记录在团队的安全文档里，并指定至少两个人能拿到。
3. **更新联系邮箱与手机**：换成团队长期使用、人员离职也不会失效的地址。账单通知、安全告警都依赖这里，写错等于没有告警。
4. **核对登录保护策略**：确认异常登录提醒已开启（若控制台提供该选项），并把通知发到公共邮箱而不是个人邮箱。

检查点：主账号已改密并绑定 MFA；联系方式为团队公共渠道；恢复方式有书面记录。

## 第三步：CAM——停止日常使用主账号

主账号权限过大，一旦泄露或被误操作，影响面是整个账号。日常运维应改用 CAM（Cloud Access Management）用户，按最小权限分配。

建议按下面的顺序落地：

1. **创建 CAM 管理员用户**：给运维负责人一个独立 CAM 用户，绑定 MFA，授予管理类权限；之后主账号只做“破窗”用途，不日常登录。
2. **按角色拆分日常账号**：例如运维、开发、只读审计各建一组 CAM 用户或用户组，权限只覆盖各自负责的产品与资源范围。
3. **禁止在主账号上保留长期 AccessKey**：程序调用、脚本、CI/CD 一律使用 CAM 用户的密钥，并设置轮换周期。主账号上如果已有 AccessKey，立刻禁用或删除。
4. **最小权限原则**：能用只读就不要给写；能限定到某产品就不要给全局；临时提权要有到期时间或事后回收。
5. **定期复查**：人员离职、项目交接时，当天禁用对应 CAM 用户，并轮换其名下密钥。

CAM 用户怎么建、子用户与访问密钥怎么管，可以对照站点上的详细步骤：[腾讯云 CAM 子用户与访问密钥](https://www.clouddalao.com/guides/tencent-cloud-cam-sub-users-access-keys)。

检查点：日常登录已切到 CAM 用户；主账号无长期 AccessKey；每个 CAM 用户都能说出“这是谁、为什么需要这个权限”。

## 第四步：操作审计（CloudAudit）——让操作可追溯

没有审计日志，出事时只能猜。腾讯云国际的操作审计（CloudAudit / 云审计）记录控制台与 API 的管理操作，例如谁创建了 CVM、谁改了安全组、谁新建了 CAM 用户。

建议这样配置：

1. **确认已开通并开启记录**：进入操作审计相关页面，确认跟踪（Trail）或等价功能处于开启状态。
2. **选择留存位置**：把日志投递到云对象存储或可长期保存的位置，避免只依赖控制台默认短期保留。存放日志的存储桶权限要收紧，只给少数人写 / 删权限。
3. **覆盖关键面操作**：至少覆盖 CAM、安全组、费用相关高风险操作；有条件时对“创建 / 删除 CAM 用户”“修改安全组入站规则”等建告警。
4. **做一次连通性验证**：用测试 CAM 用户改一条无害标签或安全组描述，几分钟后能在审计日志里查到操作人与时间。

注意：日志存储本身会产生费用，建好后顺手在费用中心看一眼日均增量。

检查点：随便做一次测试管理操作，能在操作审计里查到记录与操作人。

## 第五步：安全组与网络入口默认策略

被扫描、被爆破的大多是公网直接暴露的管理端口。上线前把入口按下面的清单过一遍：

| 场景 | 不推荐 | 推荐 |
| :--- | :--- | :--- |
| Linux SSH | 安全组对 `0.0.0.0/0` 放行 22 | 只放行办公出口 IP，或经堡垒机 / VPN 登录 |
| Windows RDP | 对全网放行 3389 | 白名单 IP，或按需临时开放 |
| 数据库 | 绑定公网 IP 直接访问 | 放在私有网络内，仅内网或经中转访问 |
| 管理后台 | 直接暴露公网 | 加 IP 白名单或放在 VPN 之后 |

操作建议：

1. 安全组默认拒绝入站，只显式放行业务端口（如 80/443）。
2. 每条入站规则写清楚备注：用途、申请人、预计保留时间，方便日后清理。
3. Linux 实例优先使用 SSH 密钥登录，关闭密码登录。
4. 不再使用的公网 IP、弹性 IP 及时释放，既是暴露面也会持续计费。
5. 生产与测试环境使用不同安全组，避免测试规则“临时放开”污染生产。

检查点：用外部网络扫描自己的公网 IP，除业务端口外没有开放的管理端口。

## 第六步：余额 / 预算告警 + 充值通路

安全问题和费用问题常常是同一件事：被盗用的账号往往表现为突然暴涨的账单，而余额耗尽又可能导致实例停服、业务中断。做安全基线的同时，务必把费用侧提醒配好。

1. 在费用中心设置余额预警，阈值建议至少覆盖 7 天正常消耗；低于 3 天当日处理。
2. 通知对象至少两个人（或一个公共邮箱 + 一个备用渠道），只有一个人接收等于没有告警。
3. 余额预警只负责提醒，不会自动补款；需要补充余额时走 [充值](https://www.clouddalao.com/recharge)，把每笔记录对应到 UID。
4. 费用中心各页面怎么读（账户概览、账单明细、收支流水），可结合团队已有的费用中心手册一起看。

检查点：余额预警已生效，测试通知能到达；充值 UID 与台账一致。

## 一页检查清单

| 步骤 | 检查项 | 完成 |
| :--- | :--- | :--- |
| 1 | UID、国际站站点、主账号身份已记入台账 | [ ] |
| 2 | 主账号已改密并绑定 MFA，联系方式为团队公共渠道 | [ ] |
| 3 | 日常改用 CAM 用户；主账号无长期 AccessKey；权限已按最小原则拆分 | [ ] |
| 4 | 操作审计已开启并投递到长期存储，测试操作可查到 | [ ] |
| 5 | 安全组无对全网开放的 22 / 3389；业务与管理端口分离 | [ ] |
| 6 | 余额预警已配置且通知可达；充值通路与 UID 已核对 | [ ] |

这份清单建议每季度复查一次，人员变动、项目交接时也要重新过一遍。

- 操作审计日志存放位置：
- 余额告警接收人：
